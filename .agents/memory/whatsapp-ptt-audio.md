---
name: WhatsApp PTT audio
description: Evolution API behavior for sending prerecorded WhatsApp voice notes.
---

For outgoing WhatsApp voice notes, Evolution's `sendWhatsAppAudio` endpoint sends PTT media. The business expects a 30-second recording presence before delivery; this is intentional despite the added wait. For the first bronze question in a conversation, send the AI's short text intro, try the bronze audio once, then explain confirmed service details. Track attempts separately for each prerecorded clip and never replay the same clip in the conversation, including after pending or failed attempts. Never let the agent promise an audio unless the server will actually attempt it; if it cannot be sent or was already attempted, provide the most relevant confirmed service details in text instead. With encoding enabled, Evolution converts the source audio to OGG/Opus for WhatsApp; the original asset can remain unchanged.

For incoming audio, preserve a bounded inline audio base64 payload while its webhook is pending or retrying; remove it from the durable inbox after successful processing. The fallback Evolution media-download endpoint may fail when the provider does not retain the message, so stripping the only inline media copy before transcription can make every incoming voice note unreadable.

**Why:** WhatsApp PTT expects a voice-note-compatible codec, while uploaded recordings may be OGG/Vorbis. Sending ordinary audio media does not provide the same voice-note presentation, and omitting the delay skips the visible recording presence. The 30-second duration was explicitly requested to make the recording indicator last longer, so the HTTP timeout must also exceed the recording delay. The user reported that the agent promised an audio but did not send it and asked that the flow use the confirmed information available about the service.

**How to apply:** Send the original asset as base64 through Evolution's voice-audio endpoint with encoding enabled and a 30-second delay; set the provider request timeout to at least the recording delay plus network headroom. For the first bronze inquiry, deliver a short intro before the audio and relevant confirmed service details afterward. Track persisted attempts—not only successful deliveries—per clip to avoid replaying that same recording, while keeping its failure from suppressing the text answer or a distinct relevant clip. Use the provider's conversion rather than replacing or re-encoding the stored user asset.

**Why:** The durable webhook queue removes inline media to keep stored event payloads small, but the incoming-audio path can use the webhook's inline base64 directly. If the provider-side media store is unavailable, the prior sanitization discarded the only usable audio copy.

**How to apply:** Keep audio base64 only for active/retryable audio jobs and under a bounded size; strip it when the job completes. Keep provider download as fallback and log media retrieval/transcription failures without exposing raw error details to the client.
